## 2026-07-28 — PII-in-UI bug: diagnosis and fix
- **Confirmed by direct DB inspection that two separate PII issues existed, not one.** (1) Transaction descriptions in the ledger contained full Zelle/ACH/wire reference numbers and, in one row, a real street address (an ATM location). This was a **documented, intentional gap** in `pii_filter.py`'s original docstring — not a crash, but exactly what Luther flagged as visible in the UI. (2) Separately, `upload.py` was storing the fully unredacted original PDF text into `statements.raw_text`, even though the copy sent to the AI was correctly redacted. Nothing currently serves `raw_text` back to the frontend, so this wasn't what was visible on screen, but it contradicted the "always-on PII redaction" design intent.
- **Fix scope was Luther's explicit call, not a default assumption**: asked via AskUserQuestion whether to fix only the at-rest bug, or also close the description-embedded-PII gap — he chose both.
- **`pii_filter.py` additions**: labeled reference numbers → `[REF]`; bare 8+ digit unlabeled runs (catches Zelle-style trailing IDs) → `[REF]`; heuristic US street-address matcher → `[ADDRESS]`.
- **Gotcha caught before shipping**: the first version of the address regex had no lookbehind guard, so a date right next to a street address (e.g. a day-of-month like "04" right before the real street number) got matched as the street number instead. Fixed with a negative lookbehind so a number preceded by `/` or `-` can't start an address match.
- **`upload.py` fix**: `raw_text=full_text` → `raw_text=redacted_text` at upload.py:81.
- **Existing test data was cleared from cashflow.db at Luther's request** since it predated the fix; `merchant_map` was left intact. He'll re-upload the same 2 source PDFs next session to verify the fix live in the ledger.

## 2026-08-08 — split PII redaction by audience: identity fields vs. analytical fields
- **Luther's ask**: he wants a future chat feature ("how much did I spend in Chicago") to be able to answer against real transaction data, not `[REF]`/`[ADDRESS]` placeholders. Asked whether we could just store the unredacted original locally since the DB never leaves the machine.
- **Key realization: redaction happens *before* the extraction AI call, not after.** `pdf_extractor.py` only pulls raw text out of a PDF — there is no local, non-AI parsing step that turns raw text into structured transactions. The extraction AI call *is* the parser. So the old design (redact everything, including ref#/address, before that call) meant the real values were destroyed before any `Transaction` row ever existed — restoring `raw_text` alone wouldn't have fixed anything, since Phase 4's planned chat context (`docs/PLAN.md` 4.2) reads `Transaction`/stats rows, not `raw_text`.
- **New design, implemented**: split `pii_filter.py`'s old single `redact()` into two functions by audience:
  - `redact(text)` — identity fields only (account/routing/card/SSN). Still runs before the extraction AI call and is still what's stored in `statements.raw_text`. These have zero analytical value and stay redacted everywhere, always.
  - `redact_transaction_text(text)` — ref-number/address only. Applied **only** to the payload sent to the categorization AI call (`categorizer.py::_categorize_batch`), not to storage. Categorization never needed ref#/address (only merchant name/amount/type), so this costs nothing functionally.
  - Net effect: `Transaction.description` in the DB now keeps real addresses/reference numbers permanently (extraction AI sees them once, unavoidably, since it's doing the parsing); account/routing/card/SSN never reach any AI provider at all; categorization never sees ref#/address either.
- **Confirmed no knock-on breakage**: `merchant_mapper.py`'s word-subset matching (`find_related_entry`/`find_matching_transactions`) still works — canonical patterns come from the AI's `suggested_key`, generated from the now-categorization-redacted description, so patterns stay clean; the extra ref#/address words now present in `tx.description` just become harmless extra words in the subset comparison.
- **Tests**: rewrote `test_pii_filter.py` to test the two functions separately (56 tests passing, up from 53) — including explicit regression tests that `redact()` now *preserves* ref numbers/addresses rather than stripping them.
- **Not yet done**: existing statements #1/#2 in `cashflow.db` still have the old `[REF]`/`[ADDRESS]` placeholders baked into their descriptions from before this change — that's permanent for those rows (extraction can't be re-run after the fact). Luther will need to re-upload the same 2 PDFs again to see real data end-to-end.
- **Future direction discussed, not implemented**: Luther wants a Phase 4 stretch where a synced calendar helps the chat agent match transactions to likely events before adding them to inquiry context. Noted for `context_builder.py` design later, no action needed now.

## 2026-08-08 (cont'd) — e2e sections 3 + 4 completed; categorization architecture fix ("option 2")
- **Ran the rest of e2e section 3 (ledger) and all of section 4 (filters) live**, all passing. Section 3.4 (pagination) needed 60 temporary synthetic rows inserted/deleted since real data alone is only 15 (below the 50/page threshold) — verified via direct API query (not just visually) that page 1+2 have zero overlap and zero gaps. Section 4 confirmed all filters including a real finding: transaction #27 (an ATM withdrawal) was categorized "Internal Transfer" by the AI despite `is_internal_transfer=False` — the exclude-transfers toggle (flag-based) correctly left it visible, proving the filter itself was right and the AI's category assignment was wrong. That finding is what triggered the discussion below.
- **Diagnosed the actual root cause with Luther before fixing anything**: extraction and categorization are two *independent* AI calls. Extraction computes `is_internal_transfer` from its own rule (explicit patterns like "Online Transfer To Chk", "Zelle To Self"). Categorization is a separate, later call that only ever receives `{id, description, amount, type}` — it never sees the `is_internal_transfer` flag extraction already decided, so it can (and did) make its own contradictory judgment about the same transaction.
- **Talked through two fix options, Luther chose the architectural one over the prompt-only one**: (1) prompt-only — tighten the "Internal Transfer" category description to exclude ATM/cash withdrawals, a narrower probabilistic rule that could still misfire elsewhere; (2) architectural — make `is_internal_transfer` the deterministic source of truth, chosen.
- **Implemented in `categorizer.py::categorize()`**: transactions are split by `is_internal_transfer` before anything else runs. Flagged ones get `category="Internal Transfer"`, `confidence=1.0` directly in code — no merchant-map lookup, no AI call, no merchant-map entry created (transfer descriptions carry unique per-transaction reference numbers, so a map entry for them would be useless — the flag itself reclassifies every one, fresh, from extraction, every time). Non-flagged transactions go through the exact same `apply_map()` → AI-batch flow as before. `categories_json` sent to the categorization AI now excludes "Internal Transfer" entirely (`Category.name != "Internal Transfer"`) — a structural guarantee, not just an instruction the AI could ignore; the `Category` table itself and `GET /api/categories` are untouched, so it's still filterable in the UI for rows that get it via the deterministic path.
- **`docs/PROMPTS.md` updated** per the file's own documented versioning convention (version comment as the first lines *inside* the prompt code fence, confirmed via `prompt_loader.py` that this literally gets sent to the AI as part of the system prompt — that's the project's own established convention, followed as-is rather than second-guessed): removed the now-unreachable "Internal Transfer is reserved for..." instruction, replaced with a comment explaining why it's gone.
- **3 new tests** in `test_categorization.py`: flagged transaction never calls the AI and gets deterministic assignment; "Internal Transfer" is verifiably absent from the categories JSON sent to the AI (asserted against the actual captured prompt text, not just behavior); a mixed batch (one flagged + one not) proves only the non-flagged transaction's ID appears in what's sent to the AI. 62/62 tests passing (up from 59).
- **Existing bad data (tx #27) deliberately left alone** — Luther's call: the dev DB will get wiped again once e2e testing wraps up anyway, so fixing it now would be wasted effort (and reset-and-recategorize would cost a real AI call for no lasting benefit). The code fix only prevents this going forward; not retroactive by design, confirmed as the right call given the DB's temporary state.
- **Still not committed** — pending Luther's approval per the CLAUDE.md gate.
